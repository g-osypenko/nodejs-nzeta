# Lab 5 · Рев'ю виходу AI: розбіжності зі spec і виправлення через вхід

## 1. Інструмент вимірів брехав: RPS −10 % і «затримка event loop» = роздільність таймера

- **Що:** у першій базовій лінії (оркестратор агента) досягнутий RPS скрізь був рівно 90 % від цілі (180 з 200). Затримка event loop на будь-якому навантаженні — 10,8 мс. Обидва числа — артефакти:
  - знаменником був `testRunDurationMs` k6, а він включає setup/teardown;
  - гістограма `monitorEventLoopDelay` записує весь інтервал тіку разом із роздільністю 10 мс.
- **Проти чого:** spec §9 «звіт: досягнутий RPS, затримка event loop»; правило `AGENTS.md` «метрика інструмента не приймається на віру».
- **Виправлення виходу:** `a2a0d6b` — знаменник = задана тривалість, затримка без роздільності. Базову лінію переміряно повністю, а неправильну не закомічено.
- **Зміна входу:** `AGENTS.md` (`00638fe`): метрику стенда перевіряти на контрольному прогоні з відомою відповіддю.

## 2. CPU-профіль суперечив ELU — і першим неправим був профіль

- **Що:** профіль handshake 800 RPS показав зайнятий main thread **1,5 %**, хоча ELU того самого навантаження — **30 %**. Дві причини:
  - при семплуванні 1 мс і квоті 1 vCPU майже не було зайнятих семплів;
  - агрегація за `timeDeltas` приписувала прогалини семплера (до 90 мс) наступному семплу `(idle)`.
- **Як знайдено:** контрольний прогін 250 мкс → 17 012 зайнятих семплів. Видно й ціну профайлера: ELU 76 % під ним проти 30 % без нього.
- **Виправлення виходу:** `895cd2d` — 250 мкс, частки за кількістю зайнятих семплів, у звіті прямо сказано, що профіль дає пропорції, а не абсолютну вартість.
- **Зміна входу:** `AGENTS.md` (`00638fe`): дві незалежні метрики одного явища мають узгоджуватися, інакше вимір хибний.

## 3. Прогнози, які цифри не підтвердили

- **Кеш для `loader`.** Лаба 2 записала його в spec §7 як план для Лаби 5. Виміри: handshake лінійний до 1 440 RPS, `findByKey` 0,04 мс, наш код — 4,5 % main thread. Кеш нічого не дав би, тож його відкинуто, spec §7 оновлено (`00638fe`).
- **Lazy-маршрути проти `unused-javascript`.** Агент запропонував і реалізував. `vite build` показав, що всі сторінки разом ≈ 6 КБ із 323 КБ (решта — React). Відкочено до коміту; реальне виправлення — стиснення, 324 → 90 КБ (`dc390f1`).
- **Зміна входу:** `AGENTS.md`: рішення про оптимізацію — лише за числом зі стенда до/після; прогноз зі spec — гіпотеза.

## Додатково

- **Захист спрацював проти власного клієнта:** перший прогін «після» впав — оркестратор логінив 50 користувачів паралельно й отримав `503 AUTH_BUSY`. Сервер поводився правильно, виправлено клієнта: повтор за `Retry-After` (`51efdf2`). Правило для клієнтів — `AGENTS.md`.
- **Тест метрик флакав на Windows:** `process.cpuUsage()` не зараховує CPU, коли хост витісняє потік (на машині паралельно працює стек CVAT, ≈ 20 контейнерів). Тест тепер чекає зарахованого CPU-часу, а не wall-часу (`04f8edc`).
- **Регресія в межах SLA:** login 20 RPS p99 26,8 → 34,4 мс. Два одночасні логіни тепер чекають у черзі, а не ділять ядро. Свідома ціна admission control.
- **Неакуратна історія:** зміна spec (SLA, `AUTH_BUSY`) потрапила в коміт `e45e83d` разом із пакетом — коміт spec перед цим відхилив commitlint, а файл лишився в індексі.
