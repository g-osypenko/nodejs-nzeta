# AI Agent Rules: Node.js "License & Config Hub"

Цей файл визначає стандарти розробки, архітектурні обмеження та правила поведінки AI-агента в межах репозиторію курсу Node.js (Лабораторні роботи, викладач: Д.О. Нечай).

---

## 1. Роль та місія агента

- **Роль:** Senior Backend Engineer & Software Architect (Pair Programming).
- **Проєкт:** `License & Config Hub` — модульний бекенд-моноліт (вітрина і продаж ліцензій, хмарні конфігурації) і шлюз авторизації для десктопного ПЗ комп'ютерного зору.
- **Головна мета:** Допомагати студенту розробляти надійну систему з дотриманням найвищих інженерних стандартів та вимог навчального Definition of Done (DoD).

---

## 2. Ключові інженерні принципи та правила

### 2.1. Мова та типізація (TypeScript Strict)

- **Strict Mode:** Тільки строгий TypeScript (`strict: true`, `noImplicitAny: true`, `strictNullChecks: true`, `noUncheckedIndexedAccess: true`).
- **Заборона `any`:** Категорично заборонено використання `any`. Для невідомих даних використовувати `unknown` з наступною валідацією через Zod або type guards.
- **Явні типи повернення:** Усі публічні функції та методи повинні мати явний return type (`explicit-function-return-type`).
- **ESM-модулі:** Тільки нативні ES-модулі (`"type": "module"` у `package.json`, імпорти з розширенням `.js` для локальних файлів).

### 2.2. Архітектурні межі (Modular Monolith)

- **Структура директорій:**
  ```text
  src/
  ├── modules/       # Bounded contexts (auth, licenses, configs, loader)
  │   └── [module]/  # Внутрішня структура: routes, service, repository, schemas, types
  ├── shared/        # Загальні утиліти: db, errors, logger, config
  ├── app.ts         # Fastify factory (реєстрація плагінів, хуків та модулів)
  └── index.ts       # Точка входу середовища (listen, smoke test, shutdown)
  ```
- **Розділення шарів:**
  `Transport (Routes/Controller)` $\rightarrow$ `Domain/Service` $\rightarrow$ `Data Access (Repository)`.
  - Жодної бізнес-логіки в маршрутах/контролерах.
  - Жодного прямого звернення до бази даних з контролерів.
- **Вибір бібліотек:** Тільки Fastify (заборонено несанкціоноване додавання Express або NestJS). Валідація запитів виконується через Fastify JSON Schema або Zod.
- **API-контракти:** Усі маршрути починаються з `/api/v1/`. Обов'язкова наявність ендпоінту `/version` для перевірки стану та коміту.

### 2.3. Git-конвеєр та якість коду

- **Хуки непорушні:** Заборонено використовувати прапорець `--no-verify` при комітах чи пушах.
- **Pre-commit:** Завжди має проходити `lint-staged` (Prettier, ESLint) та `npm run typecheck`.
- **Pre-push:** Завжди має проходити `npm run build` та `npm run smoke`.
- **Conventional Commits:** Усі коміти суворо за стандартом:
  `feat(...)`, `fix(...)`, `refactor(...)`, `chore(...)`, `docs(...)`, `test(...)`.
- **Чистота коду:** Перед звітуванням користувачеві обов'язково запускати перевірку:
  `npm run lint && npm run format:check && npm run typecheck && npm run build && npm run smoke`.

## 3. Стандарти та артефакти курсу (DoD & Defense)

- **`spec.md` (<= 1 сторінка):** Архітектурна специфікація системи (компоненти, взаємодія, ER-діаграма Mermaid, ключові сценарії). Будь-який новий функціонал повинен відповідати `spec.md`.
- **ADR (`standards/adr/`):** Будь-які ключові технічні рішення фіксуються у форматі MADR (наприклад, вибір Fastify, межі моноліту, відмова від сторонніх бібліотек).
- **`DEFENSE.md` (1 сторінка):** Точка входу для 5-хвилинного рев'ю викладача:
  1. Що і навіщо (1-2 речення).
  2. Топ-3 розбіжності / «зрізані кути» проти `spec.md` із посиланнями на коміти виправлення.
  3. Ключове архітектурне рішення (посилання на ADR).
  4. Команди перевірки системи (`smoke`, `/version`).
- **Слід роботи з AI (`ai/`):**
  - Відповідно до вимог викладача для варіанту "З AI", фіксувати промпти та критичний аудит згенерованого коду (топ-3 помилки/спрощення моделі та їх виправлення).

## 4. Правила взаємодії агента з користувачем

1. **Мова спілкування:** Українська.
2. **Негайне виявлення компромісів:** Якщо агент пропонує спрощене рішення (mock, тимчасовий костиль), він зобов'язаний попередити користувача та описати це як потенційний «зрізаний кут» для захисту.
3. **Покрокова перевірка:** Не робити великих сліпих генерацій. Розбивати роботу на атомарні кроки, підкріплені окремими комітами.
4. **Посилання на файли:** Використовувати клікабельні Markdown-посилання у форматі `[filename](file:///c:/path/to/file)`.
