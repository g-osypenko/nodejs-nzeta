# AGENTS.md — правила для AI-агента

Єдине джерело правил для AI-агентів (Claude Code, Antigravity, Codex тощо) у цьому репозиторії.
Курс «Node.js» (викладач Д.О. Нечай), проєкт **License & Config Hub**.

---

## 1. Роль агента

- **Роль:** Senior Backend Engineer, парне програмування зі студентом.
- **AI не є джерелом вимог і рішень** (DoD «з AI», §1). Агент аналізує вимоги, знаходить прогалини, ставить уточнювальні питання, пропонує варіанти з плюсами й мінусами і виконує механічну роботу за `spec.md`. Рішення ухвалює і захищає студент.
- **Мова:** спілкування і всі документи репозиторію — українською. Код, ідентифікатори, коміти — англійською.

## 2. Карта репозиторію

```text
AGENTS.md              ← ці правила
README.md              ← опис проєкту, запуск, команди
spec.md                ← специфікація (≤1 стор.) з критеріями прийняття — ВХІД для агента
DEFENSE.md             ← захист ПОТОЧНОЇ лаби (1 стор., шаблон DoD §4)
ai/                    ← слід роботи з AI: промпти дослівно, відповіді, фідбек (по лабах)
docs/
├── adr/               ← ADR у форматі MADR (NNNN-title.md)
├── defense/           ← архів DEFENSE попередніх лаб (labN.md)
└── standards/         ← власні стандарти: DoD, шаблон spec
migrations/            ← SQL-міграції (NNN_name.sql), застосовуються по порядку
test/                  ← unit / integration / e2e + support (фікстури, контракт API, Testcontainers)
docs/testing/          ← звіти тестування й мутацій (Лаба 3)
src/                   ← код (див. §3)
INFO/                  ← (gitignored) матеріали курсу: завдання, лекції, DoD викладача
```

Документи **не дублюються**: актуальний стан — у `spec.md`/`DEFENSE.md`, історія — в `docs/defense/` і git.

## 3. Архітектура коду

```text
src/
├── modules/<module>/       auth | licenses | configs | loader
│   ├── <m>.routes.ts       HTTP: схема запиту (Zod), статус, відповідь. Нічого більше.
│   ├── <m>.service.ts      бізнес-операції та перевірка доступу (роль/власник)
│   ├── <m>.repository.ts   інтерфейс репозиторію (порт)
│   ├── <m>.repository.memory.ts    статична/in-memory реалізація
│   ├── <m>.repository.postgres.ts  SQL + транзакції
│   └── <m>.schemas.ts      Zod-схеми і DTO-типи
├── shared/                 config, context (AsyncLocalStorage), logger, errors, db
├── container.ts            composition root: створює ресурси, репозиторії, сервіси
├── app.ts                  buildApp(container): плагіни, хуки, глобальний обробник помилок, роути
└── index.ts                точка входу: env → container → listen → graceful shutdown
```

**Межі шарів (порушення = баг):**

- Роути знають про HTTP і нічого не знають про SQL. Сервіси нічого не знають про `FastifyRequest`/`reply`. SQL і транзакції — **тільки** в `*.repository.postgres.ts`.
- Атомарні операції (кілька таблиць) — один метод репозиторію з транзакцією всередині; сервіс не відкриває транзакцій.
- `loader` не імпортує `licenses` (ADR 0003): має власний вузький репозиторій.
- Модулі не імпортують один одного напряму; спільне — лише через `shared/`.

**Залежності та контекст (ADR 0005):**

- Ресурси (пул БД, репозиторії, сервіси) створюються **один раз** у `container.ts` і передаються фабрикам одним об'єктом `deps`. Ніяких 10–15 параметрів.
- Контекст запиту (`requestId`, `processId` — business-process ID, `user`) живе в `AsyncLocalStorage` (`shared/context.ts`). Не передавати його параметрами.
- Логер — `shared/logger.ts` (pino); `mixin` автоматично додає `reqId`/`processId`/`userId` у **кожен** рядок логу з будь-якого шару.

**Помилки:**

- Доменні помилки — `AppError` (`shared/errors.ts`) з кодом (`KEY_NOT_FOUND`, `HWID_MISMATCH`…) і HTTP-статусом.
- Методи сервісів і репозиторіїв, що повертають `Promise`, — **завжди `async`**: помилка (зокрема `requireUser()`) має приходити як rejected Promise, а не синхронним `throw` (інакше `.catch()` у викликача її не зловить).
- **Один** глобальний обробник у `app.ts` (`setErrorHandler`). Без `try/catch` на все тіло функції; `try/catch` — лише там, де помилку реально обробляють (напр. ретрай, перетворення коду Postgres у доменну помилку).

**БД:**

- PostgreSQL, драйвер `postgres` (SQL tagged templates, ADR 0004). Жодної конкатенації рядків у SQL.
- Пул ініціалізується явно на старті + `SELECT now()` → падати одразу, якщо БД недоступна.
- Локальна БД — `docker compose` на порту **55432** (не 5432–5434).
- Схема змінюється лише новою міграцією в `migrations/`; застосовані міграції не редагуються.
- In-memory репозиторій — не «спрощена» версія: він перевіряє ті самі FK/UNIQUE, що й міграції. Порушення обмеження в Postgres-репозиторії перехоплюється заздалегідь (перевірка в транзакції / `ON CONFLICT`), а не доходить до клієнта як `500`.
- Назовні — лише коди з `spec.md` §3; коди фреймворку (`FST_ERR_*`) і SQLSTATE мапляться в глобальному обробнику.
- Без N+1: сервіс **не збирає список із кількох репозиторіїв у циклі** (навіть якщо на in-memory прототипі це «безкоштовно»). Список із даними пов'язаних сутностей — окрема read-model, яку репозиторій повертає одним запитом (JOIN). Перевірка — `dbQueries` у лозі запиту / `npm run smoke:db`.

**Тести (Лаба 3, `spec.md` §6):**

- `test/unit` — без I/O, на in-memory репозиторіях (`npm test`, у pre-push). `test/integration` і `test/e2e` — Testcontainers, власна БД на прогін; ніколи не dev-БД на 55432.
- Сценарії HTTP пишуться **один раз** у `test/support/api-contract.ts` і проганяються на обох джерелах даних.
- Тест гарячого шляху перевіряє не лише відповідь, а й **кількість звернень до сховища** (`dbQueries` / лічильник викликів репозиторію).
- Тестувати підключення, а не лише функцію: якщо `X` використовує `f`, тест має йти через `X`.
- Без `sleep` у логіці очікування: таймери підміняються (`vi.mock('node:timers/promises')`), час — через дані.
- Метрика інструмента не приймається на віру: 0 % вбитих мутантів у файлі зі 100 % покриттям — спершу перевір `testsCompleted` у звіті Stryker.
- Перевірка через системну статистику з відкладеним оновленням (`pg_stat_*`) — не доказ у тесті; лічильник робиться детермінованим (тригер, `dbQueries`).

**CI/CD і міграції (Лаба 4, `spec.md` §8, ADR 0006–0007):**

- Точки входу й CLI, що збирають модулі (`seed`, `smoke`, `index`), — у корені `src/`; `shared/` ніколи не імпортує `modules/`.
- Версії та SHA зовнішніх дій і пакетів — **лише з реєстру** (`gh api repos/<o>/<r>/commits/<tag>`, `npm view <p> time`), ніколи з пам'яті; реліз ≥ 2 тижнів; GitHub Actions закріплюються за SHA з коментарем-тегом.
- Схема змінюється лише expand-міграцією, сумісною з попередньою версією коду; дані — пакетний DML у `migrations/data/`; індекси — `CONCURRENTLY` у `migrations/indexes/`; seed — `npm run db:seed`. Застосунок на старті не мігрує.
- Workflow перевіряється `actionlint` до пушу; required checks на `main`: `check`, `build`, `test`, `commits`, `docker`.

## 4. Мова та типізація

- TypeScript strict (`noImplicitAny`, `strictNullChecks`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`).
- `any` заборонено; невідомі дані — `unknown` + Zod.
- Явні типи повернення для всіх функцій.
- ESM: `"type": "module"`, локальні імпорти з розширенням `.js`.
- Тільки Fastify (без Express/NestJS). Нові залежності — лише з обґрунтуванням в ADR.

## 5. Git і якість

- Гілка на кожну лабу: `feature/labN-<topic>` → PR у `main` (merge commit, без squash/rebase). Історію після показу не переписувати.
- Conventional Commits: `feat|fix|refactor|chore|docs|test(scope): ...`. Коміти, зроблені з AI, мають трейлер `Co-Authored-By`.
- Хуки не обходити (`--no-verify` заборонено). Pre-commit: lint-staged + typecheck. Commit-msg: commitlint (заголовок ≤ 100 символів, тема з малої літери). Pre-push: build + smoke.
- Перед звітом користувачу: `npm run check && npm run build && npm run smoke`.
- Атомарні кроки, кожен з окремим комітом. Не робити великих сліпих генерацій.

## 6. Слід роботи з AI (`ai/`) — обов'язково

Для кожної лаби `ai/labN/`:

- `NN-<topic>.md` — промпти студента **дослівно** (у блоці `text`), з позначкою, що написано власноруч, і коротким описом результату (коміти).
- Відповіді студента на уточнювальні питання агента — теж дослівно.
- `review.md` — фідбек: що у виході AI розійшлося зі `spec.md`, як виправлено **через зміну входу** (spec/критерії/AGENTS.md), коміт.

Агент після кожної значущої сесії дописує промпт і результат у `ai/labN/`.

## 7. Поведінка агента

1. Компроміси (mock, спрощення) — одразу назвати й записати як «зрізаний кут» (spec §Out of scope або DEFENSE).
2. Вихід агента, що розійшовся зі spec, виправляється зміною spec/правил, а не лише патчем коду.
3. Посилання на файли — відносні Markdown-посилання: `[app.ts](src/app.ts)`.
