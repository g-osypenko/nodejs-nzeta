# 5. Композиція: ручний composition root + контекст запиту в AsyncLocalStorage

- **Статус:** Прийнято
- **Дата:** 2026-11-05

## Контекст

Завдання 2 вимагає керувати залежностями без протягування 10–15 параметрів. Шари мають отримувати ініціалізовані ресурси (пул БД, репозиторії), користувача-ініціатора і **business-process ID**, який автоматично потрапляє в кожен лог з будь-якого рівня.

Специфіка проєкту:

- Кожен модуль має **дві** реалізації репозиторію: in-memory (статичний прототип, smoke у pre-push) і Postgres.
- Одночасно в рантаймі працює **одна** з них, її обирає `DATA_SOURCE`. Це сценарій 2 з лекції «Декомпозиція і композиція» (§4.14).
- Один бізнес-процес може тягнутися через кілька HTTP-запитів: створення замовлення → вебхук провайдера → перегляд замовлення.

## Чинники рішення

1. Сервіси не знають конкретних реалізацій репозиторіїв (заміна memory ↔ Postgres без змін у сервісах).
2. Контекст запиту доступний будь-якому шару без параметрів функцій.
3. Мінімум магії й рантайм-залежностей: стек викликів має лишатися прозорим для профілювання в Лабі 5 (ADR 0002).
4. Помилка зв'язування має виявлятися на етапі компіляції, а не в рантаймі.

## Рішення

1. **Ресурси та сервіси.** [`createContainer(config)`](../../src/container.ts) створює дані залежно від `DATA_SOURCE`, потім сервіси (`createXService({ repo, ... })`). Роути отримують готові сервіси через `buildApp(container)`.
2. **Контекст запиту.** [`shared/context.ts`](../../src/shared/context.ts) тримає в ALS `{ requestId, processId, user, dbQueries }`.
   - `onRequest` відкриває контекст.
   - `preValidation` повертає його після парсингу тіла через `AsyncResource`.
   - Auth-хук кладе користувача.
   - Сервіси викликають `requireUser()` / `requireRole('ADMIN')`.
3. **Business-process ID.** Береться із заголовка `X-Process-Id` або генерується; повертається в заголовку відповіді й зберігається в `orders.process_id`. Вебхук «приєднується» до процесу замовлення (`adoptProcessId`), тож увесь checkout корелюється в логах одним ID.
4. **Логер.** Модульний pino ([`shared/logger.ts`](../../src/shared/logger.ts)); `mixin` додає `reqId`, `processId`, `userId` у **кожен** рядок. Лічильник `dbQueries` інкрементує драйвер БД.

## Наслідки

**Позитивні**

- Перехід зі статики на Postgres (`dafc25c`) у шарі застосунку змінив лише `container.ts` і додав мапінг 503 у глобальний обробник. Жоден роут чи сервіс не змінився.
- У логах один `processId` проходить через `POST /orders` → `POST /payments/webhook` (перевіряє `npm run smoke`).
- Лабі 3 не потрібен мок-фреймворк: unit-тести сервісів отримують in-memory репозиторії.

**Негативні / компроміси**

- Логер і `requireUser()` — прямі імпорти (сценарій 3 з §4.14). Це свідоме порушення IoC рівно на один рядок.
- Контекст губиться в коді, що виходить за межі запиту (таймери, фонові задачі). Там `getContext()` повертає `undefined`, і поля логу просто відсутні.
- `dbQueries` рахується у хуку `debug` драйвера. Під навантаженням запит, що чекав вільне з'єднання, може потрапити в контекст іншого запиту — це діагностика, а не облік.
