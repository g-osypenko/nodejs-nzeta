# 9. Вимірювання продуктивності: k6 (відкрита модель) + стенд з фіксованими ресурсами + вбудовані метрики Node

- **Статус:** Прийнято
- **Дата:** 2026-11-09

## Контекст

Завдання 5: знайти боттлнеки **за даними з реально запущеної системи**. Потрібні базова лінія з p50/p95/p99, повтори й розкид, CPU проти очікування, RAM і аналіз БД. Висновки звіряються з цифрами до і після змін, тож прогони мають бути порівнянні й відтворювані однією командою.

## Чинники рішення

1. Чесний хвіст латентності: генератор не повинен знижувати навантаження, коли сервер сповільнюється.
2. Відтворюваність: однакові ресурси, дані й версія коду (`/version`) у кожному звіті.
3. Розрізнення «зайнятий CPU» і «очікування» (БД, пул, threadpool libuv).
4. Мінімум нових залежностей у проєкті (лекція 3: на кожну бібліотеку — «навіщо?»).

## Рішення

1. **Стенд** — [`perf/compose.yml`](../../perf/compose.yml): застосунок з образу поточного коміта (1 vCPU / 512 МБ, `LOG_LEVEL=info` як у prod), Postgres 17 (2 vCPU), k6 в окремому контейнері. Дані — детермінований `db:seed` (2 000 користувачів, 200 000 ліцензій).
2. **Навантаження** — [`perf/k6/load.js`](../../perf/k6/load.js), сценарії spec §9. Оркестратор [`scripts/perf/load.ts`](../../scripts/perf/load.ts): прогрів → знімок → вимір → знімок, 5 повторів, медіана (min–max). Сесії для кабінету створює оркестратор, щоб scrypt у `setup()` k6 не потрапляв у вимір.
3. **Сервер** — `GET /debug/runtime` (лише `DEBUG_RUNTIME=true`): CPU процесу (з потоками libuv), ELU main thread, затримка event loop (гістограма `perf_hooks`), RSS. CPU ≫ ELU → роботу роблять потоки (scrypt). Високий p99 при низьких CPU і ELU → очікування.
4. **Профіль** — V8 `--cpu-prof` ([`profile.ts`](../../scripts/perf/profile.ts)): self time за шарами (наш код, залежності, Node, GC, idle) і функціями.
5. **БД** — [`explain.ts`](../../scripts/perf/explain.ts) перехоплює SQL **зі справжніх репозиторіїв** (debug-хук postgres.js) і виконує `EXPLAIN (ANALYZE, BUFFERS)`; запис — у транзакції з відкатом.
6. **Фронт** — `lighthouse@13.5.0` через `npx` (mobile, 3 прогони, медіана), не залежність проєкту.
7. Кожен звіт містить SHA з `/version`. Якщо дерево брудне, до SHA додається `-dirty`, щоб невідтворюваний прогін не видавався за коміт.

## Наслідки

- ✅ `make load` / `make profile` / `make explain` / `make lighthouse` → `docs/perf/*.md`, сирі дані — `reports/perf/` (не в git).
- ✅ Висновки «CPU чи очікування» спираються на два незалежні виміри (CPU процесу й ELU), а не на здогадку з латентності.
- ⚠️ Генератор і стенд на одній машині (Docker Desktop): шум від хоста видно в розкиді min–max, тому 5 повторів і медіана, а не один прогін.
- ⚠️ Абсолютні числа стосуються цього стенда; переносяться **відношення** (до/після, сценарій A проти B), а не RPS на інше залізо.
- ❌ Розподілене трасування (OpenTelemetry) не впроваджено: для моноліта з однією БД вистачає профілю й EXPLAIN.
