# 3. Модульний моноліт і межі модулів; `loader` відокремлений від `licenses`

- **Статус:** Прийнято
- **Дата:** 2026-09-30 (доповнено до повного MADR 2026-11-05)

## Контекст

Система має чотири функціональні області з різними вимогами:

| Область                                        | Частота                      | Вимоги                                       |
| :--------------------------------------------- | :--------------------------- | :------------------------------------------- |
| `auth` — облікові записи, сесії, ролі          | низька                       | безпека паролів і токенів                    |
| `licenses` — тарифи, checkout, вебхук, адмінка | низька                       | транзакції, ідемпотентність, складні вибірки |
| `configs` — JSON-профілі користувача           | середня                      | валідація, upsert                            |
| `loader` — handshake десктопного клієнта       | **висока** (кожен запуск ПЗ) | SLA < 15 мс, атомарна прив'язка HWID         |

Команда — одна людина, одна БД, деплой — один процес.

## Чинники рішення

1. Ізоляція гарячого шляху `loader` від важкої логіки адмінки.
2. Простота розгортання і транзакцій (одна БД).
3. Межі, які можна перевірити (імпорти, шари).
4. Можливість у майбутньому винести `loader` окремо.

## Розглянуті варіанти

| Варіант                                        | Плюси                                                                                                  | Мінуси                                                                                                               |
| :--------------------------------------------- | :----------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| **Модульний моноліт, `loader` окремо, обрано** | Один процес і одна БД, локальні транзакції. Модулі з чіткими межами. `loader` оптимізується незалежно. | Таблицю `licenses` читають два модулі; формат ключа доводиться виносити в `shared/`.                                 |
| Моноліт без модулів (шари `routes/services/…`) | Найменше файлів.                                                                                       | Межі розмиваються: логіка `loader` змішується з адмінкою, оптимізувати гарячий шлях важко.                           |
| Мікросервіси (окремий `loader`-сервіс)         | Незалежне масштабування `loader`.                                                                      | Дві БД або спільна БД між сервісами, мережеві виклики, розподілені транзакції — непропорційно для курсового проєкту. |
| `loader` як частина `licenses`                 | Одна модель ліцензії.                                                                                  | Гарячий шлях тягне залежності адмінки (JOIN-и, платежі), важко профілювати окремо.                                   |

## Рішення

```text
src/modules/{auth,licenses,configs,loader}/   routes → service → repository (memory | postgres)
src/shared/                                   config, context, logger, errors, db, license-key
```

- Модулі не імпортують один одного. Спільне — лише через `shared/`, зв'язування — у `container.ts` (ADR 0005).
- `loader` має власний вузький репозиторій: `SELECT key, hwid, status, expires_at … WHERE key = $1` по унікальному індексу і один умовний `UPDATE` для прив'язки, без JOIN-ів.

## Наслідки

**Позитивні**

- Гарячий шлях `loader` — 1–2 SQL-запити на handshake. Це видно з `dbQueries` у лозі; `npm run smoke:db` прогоняє handshake на Postgres.
- `loader` можна винести окремо без змін інших модулів.

**Негативні / компроміси**

- Правила стану ліцензії частково дублюються: `isExpired` винесено в `shared/license-key.ts`, але `licenses` і `loader` інтерпретують статус кожен у своєму модулі.
- Модулі все одно ділять одну схему БД: JOIN `licenses ↔ users` в адмін-реєстрі (виправлення N+1) свідомо перетинає межу модулів на рівні SQL.
