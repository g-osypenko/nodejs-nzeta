# 2. Fastify як HTTP-фреймворк замість Express і NestJS

- **Статус:** Прийнято
- **Дата:** 2026-09-30 (доповнено до повного MADR 2026-11-05)

## Контекст

Найнавантаженіша частина системи — **Loader Gateway** (`POST /api/v1/loader/handshake`): його викликає кожен запуск десктопного клієнта, ціль SLA < 15 мс. У Лабі 5 передбачено навантажувальне тестування й профілювання Event Loop. Решта API (кабінет, адмінка, вебхук) — звичайний CRUD з низькою частотою.

## Чинники рішення

1. Низький оверхед на запит для `loader`.
2. Прозорий стек викликів для профілювання (Лаба 5).
3. Ізоляція модулів (модульний моноліт, ADR 0003).
4. Типізація в strict TypeScript.
5. Зрілість і підтримка.

## Розглянуті варіанти

| Варіант             | Плюси                                                                                                                      | Мінуси                                                                                                                                   |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| **Fastify, обрано** | Швидкий radix-роутер, мінімальний оверхед. Вбудовані хуки життєвого циклу і pino. Плагіни з інкапсуляцією. Хороші TS-типи. | Модель інкапсуляції плагінів (`fastify-plugin`) треба розуміти. Типи з власним логером громіздкі (`App` у `app.ts`).                     |
| Express             | Найпоширеніший, величезна екосистема.                                                                                      | Помітно нижча пропускна здатність. Немає вбудованої валідації і хуків життєвого циклу. Async-помилки в Express 4 губляться без обгорток. |
| NestJS              | DI, модулі, декоратори з коробки.                                                                                          | Рефлексія і декоратори ускладнюють профілювання. Фреймворк-лок. Надлишковий для 4 модулів.                                               |

## Рішення

Єдиний HTTP-фреймворк — **Fastify 5**. Валідація запитів — Zod у роутах: схема повторно використовується для типів DTO.

## Наслідки

**Позитивні**

- Хуки `onRequest`/`preValidation`/`onResponse` дали точку для контексту запиту (ADR 0005) і єдиного логу запиту.
- `setErrorHandler` — природне місце для **одного** глобального обробника помилок.

**Негативні / компроміси**

- Валідація через Zod у роутах замість JSON Schema Fastify: Ajv-компіляція схем і `fast-json-stringify` не використовуються. На гарячому шляху `loader` це оцінимо профайлером у Лабі 5.
- Fastify 5.12 позначив `disableRequestLogging` як deprecated, тож потрібен `LogController`. Мажорні оновлення вимагають уваги.
