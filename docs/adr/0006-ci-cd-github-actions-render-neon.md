# 6. CI/CD: GitHub Actions + образ у GHCR + стейдж на Render і Neon

- **Статус:** Прийнято
- **Дата:** 2026-11-09

## Контекст

Завдання 4: CI, що блокує мердж, і CD на стейдж, доступний з інтернету. Переконатися, що CI реально падає на порушеннях. Нова версія не отримує трафік, доки не готова (blue-green).

До цього всі перевірки були лише в git-хуках (husky). Хук обходиться через `--no-verify` або просто не встановлюється, а повідомлення комітів не перевірялися взагалі: у `main` є коміт `d07d16e` із заголовком 122 символи.

Обмеження студента: **не орендувати VPS зараз** ([`ai/lab4/01-kickoff.md`](../../ai/lab4/01-kickoff.md)). Репозиторій публічний на GitHub.

## Чинники рішення

1. Перевірка на сервері, яку автор PR не може обійти; мердж блокує сама платформа.
2. Стейдж безкоштовний, без картки, з HTTPS, доступний з інтернету.
3. Blue-green «з коробки»: трафік перемикається лише після health check.
4. Перевірене в CI = задеплоєне: той самий артефакт (образ із SHA), а не повторна збірка на платформі.
5. Перенесення на власний VPS пізніше без переписування конвеєра.

## Рішення

1. **CI** — [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml), 5 required checks: `check` (Prettier, ESLint, `tsc`), `build` (+ smoke), `test` (unit + integration з порогами покриття, e2e), `commits` (commitlint по всіх комітах PR), `docker` (образ збирається, контейнер стартує, `/version` = SHA). Actions закріплені за **SHA коміта** (тег можна переписати), версії ≥ 2 тижнів.
2. **Політика `main`:** branch protection — PR обов'язковий, усі 5 перевірок required, strict (гілка актуальна), без force-push і видалення. `enforce_admins` вимкнено: власник репозиторію лишає собі аварійний обхід.
3. **Артефакт:** job `docker` збирає образ один раз і після перевірки публікує `ghcr.io/g-osypenko/nodejs-nzeta:<sha>` (лише не з PR). CD деплоїть **цей самий** тег.
4. **CD** (job `deploy`, GitHub Environment `staging`, лише `main`): міграції трьома кроками з образу (ADR 0007) → Render deploy hook з `imgURL` → [`wait-for-version.sh`](../../scripts/ci/wait-for-version.sh) опитує `/version`, доки не побачить новий SHA, і падає, якщо під час перемикання була хоч одна не-200 відповідь → smoke стейджу.
5. **Blue-green** — zero-downtime deploy Render: новий інстанс отримує трафік після `200` на health check `/health` (він перевіряє БД); старий отримує `SIGTERM` → graceful shutdown ([`index.ts`](../../src/index.ts)).

## Наслідки

- ✅ Брудний PR не можна змерджити кнопкою; перевірка не залежить від того, чи встановлені хуки в автора.
- ✅ `/version` на стейджі доводить, який коміт задеплоєно (знадобиться в Лабі 5).
- ✅ Перехід на VPS = замінити крок «Render deploy hook» на SSH-деплой того самого образу; решта конвеєра без змін.
- ⚠️ Холодний старт free-інстансу: перший запит після простою ≈ 1 хв; `wait-for-version.sh` чекає до 90 с на запит.
- ⚠️ Виміри продуктивності (Лаба 5) — локально в Docker з фіксованими ресурсами, а не на free-стейджі.
- ⚠️ Секрети стейджу (рядок Neon, deploy hook) живуть у GitHub Environment `staging` і Render; у репозиторії їх немає.
- ❌ Мутаційне тестування в CI не запускається (≈ 10 хв на прогін) — лишається локальним `npm run test:mutation` (spec §7).
