# 11. Вхід без пароля: код і посилання на пошту, сесія в httpOnly-cookie

- **Статус:** Прийнято. Рішення власника продукту: вхід за кодом з пошти, у листі і код, і посилання, розсилка через Brevo, адмін теж входить за кодом (2026-11-18); сесія в httpOnly-cookie (2026-11-19).
- **Дата:** 2026-11-19
- **Трек:** продуктовий (`product/*`). Лабораторні гілки не змінюються.

## Контекст

Зараз вхід працює за email і паролем. Сервер видає непрозорий Bearer-токен, а фронт кладе його в `localStorage` ([ADR 0008](0008-frontend-react-same-origin.md), [`docs/product/web.md`](../product/web.md)). Власник продукту хоче, щоб у користувача не було пароля взагалі: людина вводить email і входить за одноразовим кодом з листа.

Обмеження:

- Домену ще немає, тож справжні листи поки не відправити (без SPF/DKIM/DMARC вони потраплять у спам). Розробка не має від цього залежати.
- Лабораторні тести, smoke і стенд продуктивності (`perf/`, `scripts/perf/`) входять паролем. Ламати їх на першому кроці не можна.
- Пакет `@lch/auth-core` не знає `node:crypto`, БД і HTTP ([ADR 0010](0010-extract-auth-core-library.md)). Нова логіка має прийти в нього через порти.

## Рішення

### Потік входу

1. `POST /api/v1/auth/code { email }` створює **виклик входу** (login challenge) і надсилає лист. Відповідь — завжди `202`, незалежно від того, чи існує такий email: реєстрація й вхід — один і той самий потік, тож розкривати нічого.
2. У листі є:
   - **6-значний код** — для випадку, коли пошта відкрита на іншому пристрої;
   - **посилання** `${APP_BASE_URL}/login/verify#token=…` — для входу в один клік.
3. `POST /api/v1/auth/code/verify { email, code }` або `POST /api/v1/auth/link/verify { token }` закриває виклик і створює сесію. Якщо користувача з таким email ще немає, він створюється з роллю `USER`. Адмін (`ADMIN_EMAIL`) створюється на старті з роллю `ADMIN`, як і раніше.
4. Посилання веде на сторінку SPA, а не на API. Токен передається у фрагменті `#`, тож він не потрапляє в логи сервера й заголовок `Referer`. Сторінка сама робить `POST`. Поштові сканери, які відкривають посилання `GET`-запитом без JavaScript, не «з'їдають» одноразовий токен.

### Правила виклику

| Правило                     | Значення за замовчуванням        | Навіщо                                                                      |
| :-------------------------- | :------------------------------- | :-------------------------------------------------------------------------- |
| Строк дії коду й посилання  | 10 хв (`LOGIN_CODE_TTL_MINUTES`) | Коротке вікно для перебору й перехоплення                                   |
| Хибних спроб на один виклик | 5                                | Після 5-ї виклик згорає; ймовірність вгадати ≤ 5 / 10⁶                      |
| Повторна відправка          | не частіше ніж раз на 60 с       | Захист скриньки від спаму й Brevo від витрати ліміту                        |
| Викликів на email за годину | 5                                | Разом із 5 спробами — ≤ 25 спроб на годину на адресу                        |
| Новий виклик                | гасить попередні                 | Діє лише останній лист                                                      |
| Що зберігається             | лише SHA-256 коду й токена       | Витік БД не дає живого посилання; код усе одно живе 10 хв і має ліміт спроб |

Спроби рахує БД атомарно (`UPDATE … SET attempts = attempts + 1 … RETURNING`), тож паралельні запити не обійдуть ліміт.

Нові коди помилок (`src/shared/errors.ts`):

- `INVALID_CODE` (401) — код хибний, прострочений або виклик згорів. Причину навмисно не уточнюємо.
- `TOO_MANY_REQUESTS` (429) + `Retry-After` — спрацював ліміт повторної відправки або годинний ліміт.

### Пошта — порт `Mailer`

- `MAILER=console` (за замовчуванням поза продакшеном): лист пишеться в лог на рівні `info` з полями `to`, `code`, `link`. Так код видно в терміналі під час розробки й у тестах.
- `MAILER=brevo` — HTTP API Brevo (`BREVO_API_KEY`, `MAIL_FROM`). Його додамо окремим кроком, коли буде домен. Решта коду при цьому не зміниться.
- Якщо `NODE_ENV=production` і `MAILER=console`, застосунок пише попередження на старті. Стейдж поки працює саме так, справжніх користувачів там немає.

### Сесія — httpOnly-cookie

- Cookie `lch_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` = строк сесії, `Secure` поза локальною розробкою (`COOKIE_SECURE`, за замовчуванням `true`). Значення — той самий непрозорий токен, у БД лежить лише його SHA-256 (як зараз).
- Плагін `@fastify/cookie` 11.1.5 (офіційний плагін Fastify, реліз 2026-10-27). Писати розбір cookie вручну — ризик помилок у безпековому коді заради економії однієї залежності.
- `POST /auth/logout` видаляє сесію в БД і стирає cookie.
- `GET /auth/me` працює з cookie, тож фронт більше не зберігає токен ніде.

### CSRF

Браузер сам додає cookie до запитів, тому для **мутацій, автентифікованих cookie** (`POST`, `PUT`, `PATCH`, `DELETE`), сервер перевіряє походження:

1. Заголовок `Origin` має збігатися з `APP_BASE_URL` (або з хостом запиту, якщо `APP_BASE_URL` не задано).
2. Якщо `Origin` немає, приймаємо лише `Sec-Fetch-Site: same-origin`.
3. Інакше — `403 FORBIDDEN`, сесія не застосовується.

Це перевірка за стандартними заголовками з OWASP CSRF Cheat Sheet. Разом із `SameSite=Lax` і тим, що API приймає лише `application/json` (HTML-форма такий запит не надішле), окремий CSRF-токен не потрібен. Запити з `Authorization: Bearer` CSRF-перевірку не проходять: браузер не додає цей заголовок сам.

### Перехідний період

- **Крок 1 (ця гілка):** вхід за кодом і cookie додаються **поруч** із паролем. `register`/`login` паролем і Bearer лишаються для скриптів, тестів і стенда продуктивності. Фронт переходить на код і cookie.
- **Крок 2 (окремо, за рішенням власника):** прибрати пароль. Потрібні нова expand-міграція, переписаний сценарій smoke/контракту на вхід кодом і стенд продуктивності, що входить кодом.

Міграція `002_login_codes.sql` (expand, сумісна з попереднім кодом):

- `users.password_hash` стає `NULL`-абельним: у користувача, створеного кодом, пароля немає. Старий код у такого користувача пароль не перевірить і поверне `INVALID_CREDENTIALS`.
- Нова таблиця `login_challenges` (`id`, `email`, `code_hash`, `token_hash`, `attempts`, `expires_at`, `consumed_at`, `created_at`) з індексом `(email, created_at DESC)`.

## Розглянуті варіанти

| Питання           | Обрано                              | Альтернатива                                 | Чому не вона                                                                                        |
| :---------------- | :---------------------------------- | :------------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| Сесія у браузері  | httpOnly-cookie                     | Токен у `localStorage`                       | Будь-який XSS краде сесію                                                                           |
| CSRF              | Перевірка `Origin`/`Sec-Fetch-Site` | Double-submit токен                          | Потребує стану на клієнті й заголовка в кожному запиті; same-origin SPA не отримує від цього більше |
| Посилання з листа | Сторінка SPA + `POST`, токен у `#`  | `GET /api/v1/auth/link?token=…` з редиректом | Поштові сканери переходять за посиланням і спалюють токен; токен потрапляє в логи                   |
| Реєстрація        | Неявна, при першому вході           | Окремий крок «зареєструватись»               | Без пароля реєстрація нічого не додає до входу                                                      |
| Сховище кодів     | Таблиця в Postgres                  | Redis                                        | Ще один сервіс; навантаження мізерне                                                                |
| Відправка листів  | Порт + `console` зараз, Brevo потім | Одразу Brevo                                 | Без домену листи підуть у спам; розробка не має чекати на домен                                     |

## Наслідки

- ✅ Паролів немає ні в користувача, ні в БД для нових акаунтів; KDF (scrypt) і `AUTH_BUSY` не потрібні для входу кодом. Вхід кодом — це кілька SHA-256 і запитів до БД.
- ✅ Токен сесії недоступний JavaScript сторінки.
- ⚠️ Безпека акаунта тепер дорівнює безпеці поштової скриньки.
- ⚠️ Немає ліміту запитів за IP: одна адреса може запросити коди на багато різних email. Це «зрізаний кут»: ліміт за IP додамо разом із Brevo, коли відправка почне коштувати.
- ⚠️ SHA-256 6-значного коду легко перебрати, якщо вкрали БД. Прийнятно: код живе 10 хв, а з доступом до БД зловмисник і так має все.
- ⚠️ До кроку 2 у системі два способи входу. Пароль лишається лише для ADMIN-бутстрапу та службових клієнтів.
