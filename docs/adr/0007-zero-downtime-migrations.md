# 7. Міграції без простою: фази schema / data / indexes, seed окремо, без міграцій на старті

- **Статус:** Прийнято
- **Дата:** 2026-11-09

## Контекст

До Лаби 4 мігратор ([`migrations.ts`](../../src/shared/db/migrations.ts)) застосовував кожен `migrations/*.sql` в одній транзакції. Довідник `plans` вставлявся всередині `001_init.sql`. Для одного розробника цього вистачало, але при CD з blue-green виникають ризики:

- Під час деплою **стара версія ще обслуговує трафік**, тож схема має працювати з обома версіями коду.
- `ALTER TABLE` чекає `ACCESS EXCLUSIVE`-блокування. Поки він у черзі за довгою транзакцією, у черзі стоять **усі** нові запити до таблиці. Це простій, хоча сам DDL миттєвий.
- `CREATE INDEX` без `CONCURRENTLY` блокує запис на весь час побудови, а на великій таблиці це до години. `CONCURRENTLY` не працює в транзакції, а невдала спроба лишає `INVALID`-індекс.
- `UPDATE` усієї таблиці однією транзакцією тримає блокування рядків і роздуває WAL.
- Міграції на старті застосунку з таймаутом health check дають цикл «таймаут → падіння → рестарт → знову міграція».

## Чинники рішення

1. Нова версія не отримує трафік, доки схема не готова; стара працює під час міграції.
2. Жоден крок не тримає блокування таблиці довше за секунди.
3. Кожна фаза — окремий крок CD: видно, що саме впало, і її можна перезапустити.
4. Повторний запуск безпечний (no-op або продовження з місця зупинки).
5. Без нової залежності (ADR 0004 — власний мігратор на postgres.js).

## Розглянуті варіанти

| Варіант                                                 | Плюси                                                                                                             | Мінуси                                                                                                                     |
| :------------------------------------------------------ | :---------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| **Власний мігратор із фазами, обрано**                  | Правила фаз закладені в код (транзакція / пакети / поза транзакцією); 0 залежностей; ~150 рядків, покриті тестами | Підтримуємо самі; правило «один DML / один індекс на файл» — конвенція, а не синтаксична перевірка                         |
| node-pg-migrate / Knex migrations                       | Готові CLI, down-міграції                                                                                         | Немає поняття фаз; `CONCURRENTLY` — ручне вимкнення транзакції для окремої міграції; ще одна залежність поверх postgres.js |
| Graphile Migrate / Sqitch / Flyway                      | Зрілі, Flyway вміє `executeInTransaction=false`                                                                   | JVM (Flyway) або інша модель (Graphile: idempotent current.sql); надлишково для 1 сервісу                                  |
| Міграції на старті застосунку (як було б «найпростіше») | Не треба окремого кроку                                                                                           | Саме антипатерн із завдання: таймаут health check → рестарт; N інстансів мігрують одночасно                                |

## Рішення

1. **Три фази, три кроки CD, три команди** (`npm run db:migrate -- --phase=…`, без прапорця — усі по черзі):
   - `schema` — `migrations/NNN_*.sql`: транзакція на файл, `lock_timeout = 5s` через `set_config(…, true)`; на `55P03` — до 3 повторів з експоненційною паузою. Краще впасти й повторити, ніж поставити трафік у чергу. Лише **expand**-зміни: нові таблиці, nullable-колонки, нові обмеження `NOT VALID`.
   - `data` — `migrations/data/NNN_*.sql`: **один** ідемпотентний DML, що обробляє пакет (`… WHERE id IN (SELECT … LIMIT 1000)`). Мігратор повторює його в окремих коротких транзакціях, доки `count = 0`. Запобіжник — `maxBatches`. Файл записується в `schema_migrations` лише після завершення, тож перезапуск продовжує з місця зупинки.
   - `indexes` — `migrations/indexes/NNN_*.sql`: **один** `CREATE INDEX CONCURRENTLY` на файл, поза транзакцією, `statement_timeout = 0`. Перед фазою `INVALID`-індекси з невдалої спроби видаляються `DROP INDEX CONCURRENTLY`.
2. **Contract-зміни** (видалити чи перейменувати колонку, `NOT NULL` на наявну) — окремим релізом, коли попередня версія коду вже не працює (expand → migrate → contract).
3. **Seed** — окрема команда [`npm run db:seed`](../../src/seed.ts), детермінована й ідемпотентна, ніколи не міграція.
4. **Застосунок не мігрує на старті** — лише `SELECT now()` (fail fast). Міграції виконує CD **до** перемикання трафіку, тим самим образом.
5. Advisory lock на сесію мігратора: два паралельні запуски не застосують одну міграцію двічі. Тому Neon — **direct** connection, не pooler (spec §8.5).

## Наслідки

- ✅ Інтеграційні тести на справжньому Postgres доводять кожне правило: 4 пакети = 4 окремі транзакції; `INVALID`-індекс перебудовано; `55P03` під блокуванням, після звільнення застосовано ([`migrations.test.ts`](../../test/integration/migrations.test.ts)).
- ✅ Повторний запуск CD після падіння на будь-якій фазі безпечний.
- ⚠️ `001_init.sql` (довідник `plans` усередині, `CREATE INDEX` без `CONCURRENTLY`) застосовано до розділення на фази. Застосовані міграції не редагуються, тож це історичний виняток: на порожній БД він безпечний.
- ⚠️ «Один DML / один індекс на файл» перевіряється рев'ю, а не парсером SQL.
- ❌ Down-міграцій немає (forward-only): відкат — новою міграцією або попереднім образом, сумісним зі схемою завдяки expand-only.
